## 1. DVP camera protocol vs. SmartDMA

### DVP is a parallel, not serial, camera interface

The OV7670 camera used here speaks **DVP** (Digital Video Port) - an older,
parallel camera interface, different from the MIPI-CSI serial interfaces
common on newer camera modules. DVP uses:

- **8 parallel data pins** (D0..D7) - one pixel byte per clock, no
  serialization/deserialization needed.
- **PCLK** (pixel clock) - generated by the camera itself, signals "data on
  D0-D7 is valid, sample it now."
- **HREF** - high while one horizontal line of pixels is being transferred.
- **VSYNC** - marks the start/end of a full frame.
- **SCCB** (a 2-wire, I2C-like bus) - a *separate* control channel, used only
  to configure the camera (resolution, exposure, mirror/flip...). No pixel
  data goes over SCCB.

Because the camera generates PCLK/HREF/VSYNC on its own schedule (not
synchronized to the CPU), and the required throughput at 320x240@30fps is
roughly 2.3 million bytes/second, capturing this in a plain software loop
(bit-banging GPIO reads) isn't realistic - the CPU would have to sample
every single pixel clock edge in real time with no other work happening.

### SmartDMA is a programmable DMA coprocessor, not a simple DMA channel

SmartDMA is NXP's answer to that problem: a **separate, programmable
coprocessor** on MCX-family chips (distinct from a normal DMA channel, which
just copies memory A→B on fixed triggers). SmartDMA runs its own
**firmware/microcode** that understands the DVP protocol's timing directly -
it watches HREF/VSYNC/PCLK and assembles bytes into a frame buffer entirely
on its own, in parallel with whatever the main Cortex-M33 core is doing.

To use it (`source/camera/camera_capture.c`):

```c
SMARTDMA_InstallFirmware(SMARTDMA_CAMERA_MEM_ADDR, s_smartdmaCameraFirmware, ...);
SMARTDMA_InstallCallback(CAMERA_CAPTURE_CompleteCallback, NULL);
NVIC_EnableIRQ(SMARTDMA_IRQn);
SMARTDMA_Boot(kSMARTDMA_CameraWholeFrameQVGA, &smartdmaParam, 0x2);
```

- `SMARTDMA_InstallFirmware()` loads the camera-capture microcode into
  `SMARTDMA_CAMERA_MEM_ADDR` (a fixed address, `0x04000000`).
- `SMARTDMA_Boot(kSMARTDMA_CameraWholeFrameQVGA, ...)` starts the coprocessor
  running that firmware, in "one full 320x240 frame per interrupt" mode.
- When SmartDMA finishes copying a frame, it fires a hardware interrupt
  (`SMARTDMA_IRQn`) → `CAMERA_CAPTURE_CompleteCallback()` sets a
  `s_frameReady` flag.
- The main CPU just polls that flag in the `main()` loop - it never has to
  worry about pixel-level timing at all.

This is the general pattern for offload coprocessors: **the coprocessor
handles the hard-real-time part (catching every pixel on time), the main CPU
handles the logic (AI inference, display)**.

### The catch: SmartDMA needs dedicated RAM, and it isn't "free" just because the linker doesn't know about it

`SMARTDMA_CAMERA_MEM_ADDR` (`0x04000000`) turns out to be the exact starting
address of `m_sramx`, a 96KB RAM bank on this chip. The SDK's own board
linker script **doesn't declare any output section for `m_sramx`** - because
SmartDMA's firmware is loaded into it at runtime via a C function call, not
through the static linker.

This makes `m_sramx` *look* completely unused if you only check the linker
map, which is exactly what led to the (wrong) decision to reuse it for the
AI model's tensor arena. See section 3 for what happened.

## 2. Neutron NPU: what it is and how it's used

### What Neutron is

Neutron is NXP's neural-network acceleration coprocessor, built into some
MCX/i.MX chips (the MCXN947 has the "Neutron16" variant, `mcxn94x` target
name in NXP's tooling). Same pattern as SmartDMA above - it's a **separate
coprocessor** with its own driver + firmware
(`libNeutronDriver.a`/`libNeutronFirmware.a`), running in parallel with the
main core, specialized for the matrix-multiply-heavy operations (conv,
depthwise-conv...) that dominate neural network inference time.

### Models need to be converted for the NPU - it's not just a compile flag

This is the biggest practical difference from a CPU+CMSIS-NN path: CMSIS-NN
can accelerate basically any standard int8 TFLite model out of the box, but
**the NPU needs the model run through a separate conversion step first**,
using NXP's `neutron_converter` tool (package `eiq_neutron_sdk`, installed
from NXP's own package index - not on public PyPI):

```bash
neutron_converter --input model.tflite --target mcxn94x --output model_npu.tflite
```

This tool scans the model graph, finds clusters of layers the NPU supports
(conv/pool/add/etc.), and **collapses them into a single custom op called
`NEUTRON_GRAPH`** (containing microcode pre-compiled for the Neutron16
core). Any unsupported layers (rare - in this project's model, just Softmax)
stay as regular ops running on the CPU as before. For this project's FOMO
model, **31 of 32 original operators got folded into the NPU op** - a very
high offload ratio, since almost the entire compute-heavy backbone
(MobileNetV2) collapsed into one NPU-accelerated block.

### Integration: plain TFLite Micro, bypassing the higher-level SDK

The Edge Impulse SDK's own `ei_run_classifier()` entry point has no way to
register a custom `NEUTRON_GRAPH` op (it builds its own fixed op resolver
internally). So the NPU path is a separate code path
(`model_runner_npu.cpp`) that talks to TensorFlow Lite Micro directly:

```cpp
// Exactly the op resolver neutron_converter itself suggests, printed as a
// comment at the top of the header it generates:
static tflite::MicroMutableOpResolver<2> s_opResolver;
s_opResolver.AddSoftmax();
s_opResolver.AddCustom(tflite::GetString_NEUTRON_GRAPH(), tflite::Register_NEUTRON_GRAPH());

tflite::MicroInterpreter interpreter(model, s_opResolver, tensorArena, arenaSize);
interpreter.AllocateTensors();
interpreter.Invoke();  // the NEUTRON_GRAPH portion runs on the NPU automatically
```

**No manual "start the NPU" call is needed anywhere.** `neutronInit()` (the
actual hardware init function, inside the driver) is called **internally by
the NEUTRON_GRAPH kernel itself**, the first time TFLM calls its `Prepare()`
step. The coprocessor initializes itself lazily on first use - application
code just uses the standard TFLM API like any other model.

### Quantization turned out trivially simple for this model

The model's input tensor is `int8[1,64,64,3]`, quantized with
`scale=0.003922` (≈ 1/255) and `zero_point=-128`. The standard quantization
formula is:

```
quantized_value = round(real_value / scale) + zero_point
```

Since `scale ≈ 1/255`, `1/scale ≈ 255` - one pixel unit [0..255] maps to
exactly one quantized unit. Combined with `zero_point = -128`, this reduces
to just `quantized_value = pixel_value - 128` (shifting [0,255] down to
[-128,127]) - no runtime division/multiplication needed at all, which is
convenient on an MCU with no hardware FPU-heavy quantization path.

### Timing measurement note

Edge Impulse's own `ei_result.timing.classification_us` field turned out to
always read `0` on this SDK/porting combination (the clib porting layer
hard-codes `ei_read_timer_us()` to `return 0`, since bare-metal has no
generic timer source to call). Both the CPU and NPU paths instead measure
inference time by hand with the Cortex-M33's DWT cycle counter
(`DWT->CYCCNT`), converting cycles to microseconds via `SystemCoreClock` -
this gives a real, comparable number for both backends.

### Measured results

| | CPU (CMSIS-NN) | NPU (Neutron) |
|---|---|---|
| Time per inference | ~1.27 seconds | ~3.3 milliseconds |
| Relative speed | 1x | **~370-390x faster** |

## 3. Limitations encountered

### SmartDMA and the AI tensor arena physically collide in the same RAM bank

As noted in section 1, `m_sramx` looks unused in the linker map, but it's
actually the RAM SmartDMA uses to hold its own camera-capture
firmware/state while running. The AI CPU path (CMSIS-NN) originally reused
that same bank for its ~93KB tensor arena, on the (wrong) assumption that it
was genuinely free. The moment inference actually wrote real data into that
bank, it silently corrupted SmartDMA's own working state - not a crash, just
the camera going quiet: it stopped firing frame-ready interrupts after a few
frames, with no error logged anywhere.

**Fix:** the camera is fully stopped (`CAMERA_CAPTURE_Deinit()`) right
before AI inference runs, and restarted (`CAMERA_CAPTURE_Reinit()`)
immediately after. Camera capture and AI inference never touch `m_sramx` at
the same time - the tradeoff is that capture and inference run strictly
sequentially, not in parallel, which is acceptable here since inference was
already the slowest step in the pipeline either way.

**Takeaway:** on a chip with multiple coprocessors sharing distinct RAM
banks (SmartDMA, an NPU, a DSP core...), a bank that looks empty in the
linker map isn't necessarily free at runtime - check whether any
coprocessor firmware is loaded into it before reusing that memory for
something else.

### USB video streaming vs. camera capture: a genuine hardware conflict, not a software bug

This project originally also tried streaming the camera feed over USB as a
standard UVC (USB Video Class) webcam. That was abandoned - not because of
a code problem, but because of a real hardware constraint on this
particular board.

**The core issue - conflicting voltage requirements:** the MCXN947's DCDC
core voltage regulator runs at different levels depending on which
peripherals need to be fast:

- **Mid voltage (~1.0V)** is what SmartDMA camera capture needs to run
  reliably (confirmed through repeated hardware testing).
- **Overdrive (~1.2V)** is required for the USB High-Speed PHY's PLL to lock
  and function at all.

These two peripherals need **different, non-overlapping voltage levels** -
at any given moment, the chip can run the camera *or* USB HS, never both at
once.

**No hardware bypass available on this board:** the chip does have a
separate USB Full-Speed module that doesn't need Overdrive voltage, which
would sidestep the conflict entirely if it were accessible. But per the
board's own user manual (UM12018, section 2.3), the single USB Type-C
connector on FRDM-MCXN947 is hard-wired to the High-Speed controller only -
there's no way to reach the FS module without physically reworking the
board.

**Why this counts as a hardware limitation, not a software bug:** a timing
or configuration issue can usually be fixed in code. Here, the physical
requirement (the USB HS PHY's PLL genuinely cannot lock below a certain
voltage) combined with the board's fixed wiring (the connector only ever
reaches the HS controller) makes this unfixable from software, no matter
how the driver is written - USB HS and camera capture simply cannot coexist
on this exact board.

**What was tried instead:** a time-multiplexed workaround - periodically
switching between "Mid voltage, capture a few fresh camera frames" and
"Overdrive, stream that frame over USB for a few seconds," then repeating.
This genuinely worked (confirmed via `lsusb`, `dmesg`, and a sustained
`gst-launch-1.0` capture session), but produced low-frame-rate, choppy
video rather than smooth live streaming, and added real code complexity
(two voltage states, careful timing around the switch). Since the project's
actual goal (drowsiness detection) doesn't need a USB video feed - the
on-board LCD status display is sufficient - this path was set aside in
favor of the simpler LCD-only design.
